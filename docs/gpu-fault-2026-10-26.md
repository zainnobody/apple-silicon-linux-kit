# GPU render fault and plasmashell crash (2026-10-26 23:22)

Read-only analysis: kernel log, plasmashell's journal, the core dump (`coredumpctl 1991`) and the kernel and Mesa sources on the M3. Kernel 7.2.11-m3gpu+, Mesa SiliconForest `7515336` in `/opt/mesa-m3` (release build, no line information).

## What happened

| Time | Event |
|---|---|
| 23:21:38 | `tests/vk-stress.c` starts (compute only). Desktop in use: plasmashell, Firefox, LibrePods and others are GPU clients. |
| 23:22:08 | vk-stress drops from about 200 to about 105 frames/s (cause not known; before the fault). |
| 23:22:53 | GPU fault in a **render** job of plasmashell (context 18, TA and FS stages, draw 362921). Both fault banks: status `0x8492a48011`, **read of an unmapped page**, level 0, unit code `0x40`, addresses `0x5be305f400` and `0x5be305e9c0`. |
| 23:22:53 | The kernel recovers the GPU (halt, resume, new render allocators). The job fails with EIO. Its VM gets a **sticky error**. |
| 23:23:00 | plasmashell: `BO creation failed ... label=Vertex buffer`. Every `DRM_IOCTL_ASAHI_VM_BIND` fails: "VM 1 carries sticky error -5". |
| 23:23:06 | Qt tries a new GL context: `QEGLPlatformContext: Failed to create context: 3003`. Then the render thread draws a frame: `st_Clear`, `agx_clear`, `agx_get_batch`, `agx_batch_init`. `agx_encoder_allocate()` gets NULL from `agx_bo_create(dev, 0x80000, ..., "Encoder")` and reads `bo->map` (SIGSEGV at `agx_batch_init+248`, `x0 = 0`). |
| 23:23:08 | plasmashell restarts as a new process. No further GPU faults. |

vk-stress itself passed (0 wrong values). Its own context was not affected.

## Two bugs

### 1. Render job reads an unmapped address (root cause not known)

- The faulting job belongs to plasmashell, not to vk-stress (compute).
- The address lies in the client's user heap, close to the addresses Mesa was binding at that time (`0x5bfe...`). So it is a user buffer address, not a kernel or firmware address.
- Unit code `0x40` is `DCMP(4)` (decompression) in the driver's G13/G14 table (`regs.rs`). The G15 code prints only the raw value; the table may not apply to G15.
- Most likely class: a buffer (texture or render target) that is unbound or freed while a submitted render job still reads it. Heavy GPU load from another process makes jobs run later than usual, which can expose such a lifetime race. Not proven.
- This is the only GPU fault in 8 boots with the GPU stack. It came during the first heavy compute load together with desktop rendering.

### 2. Mesa crashes after the context is lost

- The kernel design: after a failed job, the VM's error is sticky. Later submits, queue creation and VM_BIND calls of that VM fail with EIO (`g15/job.rs`, `complete()`). All contexts of the process share the device and its VM, so a new GL context in the same process also fails.
- Mesa sets `ctx->any_faults` and reports `PIPE_GUILTY_CONTEXT_RESET` (`agx_pipe.c`). But the batch code does not check for a failed allocation: `agx_encoder_allocate()` (7 callers in `agx_batch.c` and `agx_state.c`) uses the BO without a NULL check.
- Effect: the process crashes, instead of getting a context reset. A desktop shell that restarts (as plasmashell did) recovers; an application can lose data.

## Fix plan

| Step | What | Risk |
|---|---|---|
| 1 | Mesa: when `agx_bo_create` fails in batch setup, mark the context as lost and turn the draw or dispatch into a no-op. Tried as `patches/mesa-asahi-lost-context-noop.patch` (2026-10-27): **not effective**, see "Lost-context test" below. | Low. Changes only the failure path. |
| 2 | Mesa: after a sticky VM error, report the reset through `get_device_reset_status`, so that robust clients (`GL_EXT_robustness`) can recreate. A full recovery needs a new device (new DRM file and VM), so a client must recreate its screen, not only its context. | Medium. Needs a design decision. |
| 3 | Reproduce the fault: desktop animation plus `vk-stress`, with Mesa BO tracing on (an `AGX_MESA_DEBUG` trace option, to be checked) and the kernel fault log. Find the buffer at the fault address. | Uses the GPU; needs a slot. |
| 4 | Fix the buffer lifetime race found in step 3 (Mesa or kernel). | Depends on step 3. |

Steps 1 and 2 do not remove the fault. They only stop the crash. Step 3 finds the cause.

## Lost-context test (2026-10-27)

`tests/lost-context-inject.c` (LD_PRELOAD) makes VM_BIND, GEM_CREATE and SUBMIT fail with EIO after a few seconds, as the G15 kernel does for a VM with a sticky error. `tests/lost-context-test.sh` and `tests/robust-reset-test.c` run the clients. Installed Mesa against `patches/mesa-asahi-lost-context-noop.patch` (built into a separate prefix):

| Client | Installed Mesa | Patched Mesa |
|---|---|---|
| `es2gears_wayland` (no reset notification) | SIGSEGV in `agx_batch_init` | SIGSEGV in `st_update_vs_constants` |
| `glmark2-wayland` (no reset notification) | SIGSEGV | SIGSEGV |
| `robust-reset-test` (LOSE_CONTEXT_ON_RESET) | reset seen, no crash | reset seen, no crash |
| `vkcube` (Vulkan) | no crash | no crash |

The crash after the 23:22 fault is reproduced without a GPU fault. A client that asks for reset notification (as KWin does) already survives with the installed Mesa: the failed submit reports the reset, and Mesa's GL layer then makes every call a no-op. A client without reset notification (plasmashell, es2gears) crashes in both cases: the GL layer itself uploads into buffers that the driver cannot create once the whole VM refuses new memory. The patch only moves the crash, so it is not installed.

The kernel makes the error sticky for the whole VM on purpose (`g15/job.rs`, `finish()`): after a failed job, the firmware may still read that job's memory, so the job's mappings are quarantined and all mapping changes of the VM are refused. A per-queue error would let the rest of the process work, but it changes that safety rule. Open question for the kernel: can mappings that the failed job does not use stay changeable?

## A repeatable real GPU fault (2026-10-27)

llama.cpp with the local test switch `GGML_VK_HK_TILES=s` (only the small `mul_mm` tile, not a valid choice for Honeykrisp; `ane-linux/llm/llama-vk-honeykrisp-test-switches.patch`) faults the GPU on every pp512 run of Llama 3.1 8B Q4_0: a compute job writes far outside the user heap (`write unmapped level 0 unit 0x1`, va `0x42d06738940` and `0x42d0673b8c0`, 08:39:55). The kernel recovers, the VM gets its sticky error, and llama.cpp stops with `vk::DeviceLostError`. Other processes keep working. This is a llama.cpp shader setting problem, not a fault in normal use, but it is a way to cause a real fault on purpose: for the lost-context test with a real fault, and for the per-queue error question. Do not run it on the M3 without the coordinator's go (it faults the GPU).

## Soft faults are not the cause

The G15 kernel never turns soft faults on (`g15/mod.rs`: `soft_faults()` returns `false`), and it does not advertise `DRM_ASAHI_FEATURE_SOFT_FAULTS`. So Mesa does not emit reads that rely on a soft fault (`agx_has_soft_fault()` is false). The read at `0x5be305f400` is a real bug, not an expected read.
